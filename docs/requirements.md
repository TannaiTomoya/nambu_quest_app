南部もぐり観光RPG 要件定義

1. アプリの概要

1.1 目的

南部もぐりを知らない旅行者に、3〜5分の2D探索型RPGを通じて南部もぐりの装備・送気・海底作業への関心を持ってもらい、種市歴史民俗資料館などの公式観光情報へ誘導する。

1.2 提供価値

旅行者に、長い観光情報を読む前に短い疑似体験を提供する

プレイヤーの選択に応じた見どころを提示する

ゲーム完了後の公式ページ遷移を計測する

洋野町を「知らない場所」から「訪問候補」へ変えられるか検証する

1.3 技術構成

フロントエンド：Unity / C#

バックエンド：Python / FastAPI

通信形式：HTTP + JSON

初期データ保存：JSONまたはSQLite

外部リンク：公式詳細ページ、Google Maps

1.4 MVPの範囲

1マップ

3探索地点

主な資源は空気

持ち帰り記録は最大2件

プレイ時間は3〜5分

FastAPIとの通信はゲーム終了時と外部リンク遷移時を中心とする

主推薦先は種市歴史民俗資料館

補助導線としてGoogle Mapsと承認済みイベント情報を表示する

2. 想定ユーザー

2.1 初期テスト対象

国内の18〜35歳程度

個人旅行または東北周遊に関心がある

洋野町や南部もぐりを詳しく知らない

スマートフォンやゲーム操作に抵抗がない

開発関係者ではない

2.2 将来の対象候補

八戸周辺や東北を旅行中の国内旅行者

宿泊施設の利用者

将来的には英語利用の個人旅行者

2.3 利用場面

宿泊施設の受付・ロビー・ラウンジ

地域イベントや観光拠点

QRコードからゲームを開始する

プレイ後に公式観光情報を確認する

3. 必須機能

3.1 Unity側

3.1.1 タイトル・開始

タイトル画面を表示する

「ゲーム開始」ボタンを表示する

短い操作説明を表示する

「空気には限りがあり、すべての地点には行けない」と伝える

3.1.2 プレイヤー操作

2Dキャラクターを移動できる

マップ内の探索地点に近づける

探索地点を調べられる

帰還地点へ戻れる

3.1.3 空気管理

初期空気を100とする

現在の空気量を画面に表示する

各地点の総消費空気を事前に表示する

安全帰還に必要な予備空気を15とする

空気不足時は事故演出ではなく、帰還指示または作業中断として扱う

3.1.4 3つの探索地点

以下の3地点を実装する。

近距離地点

テーマ：重装備の基本

消費空気：25

作業：装備状態の確認

取得記録：装備確認記録

中距離地点

テーマ：送気と船上連携

消費空気：40

作業：送気経路または通信状態の確認

取得記録：送気連携記録

遠距離地点

テーマ：海底作業と歴史

消費空気：60

作業：海底作業対象の調査

取得記録：海底作業記録

3.1.5 持ち帰り記録

記録は最大2件まで選べる

物理的なインベントリではなく、選択した調査記録として扱う

帰還時に持ち帰る記録を確定する

プレイヤーが選ばなかった記録を確認できる

3.1.6 帰還

プレイヤーが任意のタイミングで帰還を選べる

帰還後にプレイ結果をまとめる

残り空気、訪問地点、取得記録、プレイ時間を確定する

3.1.7 FastAPIへの送信

ゲーム終了時に、以下をFastAPIへ送信する。

匿名セッションID

訪問地点

完了した作業

選択した持ち帰り記録

残り空気

安全帰還の成否

プレイ時間

3.1.8 推薦結果の表示

FastAPIから受け取った以下を表示する。

関心テーマ

推薦見出し

推薦理由

称号（決定的に1件選ばれた結果）

豆絞り柄（候補内ランダムで選ばれた結果）

種市歴史民俗資料館の紹介

公式詳細ページへのボタン

Google Mapsへの補助ボタン

主CTA文言：

ゲームに登場した南部もぐりの装備と記録を実物で見る

報酬表示は資料館案内より前面に出しすぎない。抽選結果によって公式情報へのアクセスを制限しない。

3.1.9 通信失敗時

通信中であることを表示する

通信失敗時もゲームが停止しない

固定の共通報酬（共通称号・共通豆絞り柄）と固定の資料館案内を代替表示する

例：称号「無事に帰還した南部もぐり」、豆絞り柄「基本柄」

再送は1回までとする

通信失敗を理由に、結果画面や資料館CTAを非表示にしてはいけない

3.2 FastAPI側

3.2.1 API起動

FastAPIアプリを起動できる

/docs でAPI仕様を確認できる

Unityからアクセスできる

3.2.2 推薦API

エンドポイント：

POST /analyze

役割：

Unityからプレイ結果を受け取る

入力値を検証する

透明なルールベースで関心テーマを判定する（乱数を使わない）

関心テーマに紐づく称号を、説明可能な条件で決定的に1件選ぶ（乱数を使わない）

テーマに対応する豆絞り柄候補（有効な3〜5件）から1件をランダムに選ぶ

推薦文、報酬結果、観光情報を返す

ゲーム完了と報酬キーを記録する

初期の関心テーマ：

equipment：装備

air_supply：送気と連携

underwater_work：海底作業と歴史

safety：安全予備を残して帰還したプレイ（称号グループとして扱う）

3.2.3 推薦・報酬ルール

テーマ判定（乱数なし）：

装備確認記録を選択 → equipmentを加点

送気連携記録を選択 → air_supplyを加点

海底作業記録を選択 → underwater_workを加点

同点の場合：持ち帰り記録の選択順を優先する

判定不能時は共通の資料館案内を返す

称号決定（乱数なし・同じ入力なら同じ称号）：

テーマに紐づく称号候補を display_order などの固定順で管理する

主テーマ、持ち帰り記録の選択順、returned_safely、remaining_air、safety条件から説明可能な規則で1件を選ぶ

returned_safely が false の場合、安全帰還称号を出さない

称号の処理経路では random や choice などの乱数処理を使用しない

豆絞り柄（ここだけ乱数を使用）：

テーマに対応する有効な候補3〜5件から1件をランダムに選ぶ

報酬の制約：

現金や換金可能な景品、ログイン、メール、個人情報、課金、有料ガチャ、配送・当選連絡を扱わない

デジタル表示だけで完結させる

コレクション保存はMVPでは実装しない

3.2.4 コンテンツ管理

以下をFastAPI側で管理する。

施設名

日本語の短い説明

公式詳細ページURL

Google Maps URL

掲載中／非掲載

更新日時

Unity内にURLを直接固定しない。

3.2.5 リダイレクト・計測

エンドポイント：

GET /redirect/{destination_id}

役割：

クリックを記録する

匿名セッションIDと遷移先を記録する

公式ページまたはGoogle Mapsへ転送する

最低限記録するイベント：

game_started

game_completed

recommendation_displayed

official_detail_clicked

map_opened

3.2.6 イベント情報

初期は担当職員が確認した最大3件を手動登録する

イベント名、短い説明、開始日、終了日、公式URL、掲載状態を持つ

終了日を過ぎたイベントは自動非表示にする

イベントは主推薦ではなく補助カードに表示する

4. 余裕があれば追加する機能

優先度の高い順に追加する。

4.1 プレイ前後の関心度

プレイ前に訪問意向を1〜5で回答する

プレイ後に同じ質問へ回答する

変化量を記録する

4.2 訪問候補として保存

「訪問候補として保存」ボタンを表示する

押下イベントを記録する

4.3 QR流入元の判定

受付用QRとラウンジ用QRでURLを分ける

流入元をセッションに保存する

設置場所別の開始率・完了率を比較する

4.4 簡易集計画面

ゲーム開始数

ゲーム完了数

公式ページ遷移数

Google Maps起動数

流入元別の件数

4.5 英語表示

日本語版の動作が安定した後に追加する

操作説明はアイコンと短文を中心にする

4.6 イベント自動取得

ハッカソン後の候補とする

初期版では実装しない

公式ポータルからの取得可否を確認してから設計する

5. 非機能要件

5.1 操作性

初見の利用者が30秒以内に基本ルールを理解できる

マウスまたはキーボードで操作できる

画面上の文字量を少なくする

重要な操作をアイコンと短い説明で示す

5.2 性能

推薦結果は原則5秒以内に表示する

ゲーム中の移動や空気処理はUnity内で完結させる

ゲーム中に頻繁なAPI通信を行わない

5.3 可用性

FastAPIが停止していても、ゲーム本編は最後まで遊べる

API通信に失敗した場合は固定の観光案内を表示する

5.4 データ

氏名、住所、電話番号などの個人情報を取得しない

匿名のセッションIDで行動を記録する

同じ操作の重複記録を可能な範囲で防ぐ

テスト用データと本番用データを区別する

5.5 セキュリティ

Unityから受け取ったデータをそのまま信用しない

数値範囲と文字列形式を検証する

外部遷移先は事前登録した公式URLだけに限定する

APIキーや秘密情報をUnity側へ埋め込まない

5.6 保守性

UnityとFastAPIの役割を分離する

推薦文とURLはFastAPI側で変更できる

ルールベース判定を別関数に分けられる構造にする

初期版ではファイルを増やしすぎない

5.7 表現上の配慮

架空の軽量装備を登場させない

南部もぐりを宝探しとして表現しない

歴史資料を海底に不自然に配置しない

事故や死亡を娯楽的な演出にしない

安全判断を予測可能な空気管理として表現する

実在展示の有無を確認してから断定する

6.3 UnityとFastAPIの境界

Unity側：

移動

衝突判定

空気減少

探索

記録選択

帰還判定

画面表示

称号・豆絞り柄の表示

通信失敗時の固定報酬表示

FastAPI側：

入力検証

推薦判定（テーマ判定・乱数なし）

称号の決定的選択（乱数なし）

豆絞り柄の候補内ランダム選択

コンテンツ管理

クリック計測

ログ保存（報酬キーを含む）

外部URLへの転送

6.4 史実との整合

ゲーム内テーマは資料館の実在展示または公式資料と対応させる

展示物の正式名称は担当職員または資料館関係者へ確認する

確認前は「展示予定」「展示候補」として扱う

ゲーム内の説明は短くし、詳細は公式ページへ委ねる

6.5 計測方法

以下の算式を統一する。

ゲーム完了率game_completed ÷ game_started

公式詳細ページ遷移率official_detail_clicked ÷ game_completed

Google Maps起動率map_opened ÷ game_completed

初期の暫定目標：

ゲーム完了率：70%以上

公式詳細ページ遷移率：20%以上

Google Maps起動率：10%以上

これらは実績ではなく、次の検証へ進むための暫定基準とする。

6.6 初期検証

国内の旅行経験者5人でルール理解を確認する

その後、10〜20人で完了率と遷移率を測る

受付QRとラウンジQRは別URLにする

開発関係者だけでテストしない

「なぜこの推薦が出たと思うか」を質問する

同じ入力条件なら同じ称号になることを確認する

同じ称号でも異なる豆絞り柄が出る可能性があることを確認する

7. 完了条件

MVPの完了条件は以下とする。

Unityで3地点を探索できる

空気100と安全余力15が表示される

3地点すべてを安全に回れない

記録を最大2件選択できる

帰還後にFastAPIへプレイ結果を送信できる

FastAPIが推薦テーマと資料館案内を返せる

称号は関心テーマから決定的に1件選ばれ、乱数を使わない

豆絞り柄だけが候補内ランダムで選ばれる

同じ入力条件なら同じ称号が返る

Unityで主CTAとGoogle Mapsボタンを表示できる

公式ページとGoogle Mapsへのクリックを記録できる

API停止時にも固定の共通報酬と資料館案内を表示できる

資料館CTAが必ず表示される
